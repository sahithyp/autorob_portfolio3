A dance is a list of states. Each state sets joint targets (target), how long to hold (hold, seconds), where the body glides to (base: x, y, z, yaw) and which state comes next (transitions + on_arrival). Joint names are in the table above.

    The robot

    Steve is a Minecraft-style humanoid described in a URDF file: 25 links made of boxes and 12 movable joints. One Minecraft pixel is 0.04 m, so the body is 8×12×4 px, the head is a 0.32 m cube, and each limb is split into pieces so it can bend. The robot faces +x; every arm and leg joint turns about the y axis.

    One part is not from Minecraft: a prismatic antenna on top of the head, which slides up 0–0.3 m. The joint tree matches the course's mini humanoid test robot, and the antenna gives the dance a joint that moves in a straight line instead of rotating, which makes a nice beat accent. The face (eyes, nose, mouth), hair, sleeves and shoes hang off fixed joints, so they ride along with their parent link.

    The choreography

    The dance is a finite state machine: 48 states, one per beat, at 120 BPM, so the loop is exactly 24 seconds. Each state is a setpoint for the joints. When the robot has reached it (every named joint within the state's epsilon) the machine follows the state's on_arrival transition to the next beat, and the last state loops back to the first.

    45–48FinaleDeep crouch, then arms-up wrist spin and a settle, ready to loop.

    What makes it a moonwalk

    The illusion is a mismatch between the feet and the body. Every beat one leg swings: thigh forward, knee folded, toe down. The other supports: straight and leaning back. They swap on the next beat, with the opposite arm swinging forward, exactly like walking forward. Meanwhile the whole robot slides backwards at a constant 0.16 m/s, so the planted foot never seems to push off the ground.

    Joints alone cannot move the robot's base, so I gave each state two optional extras, described below. 

    // one beat of the moonwalk (trimmed): joints, then where the body is gliding to
{ "name": "moonwalk_a_1", "epsilon": 0.08,
  "hold": 0.5,                                   // at least this many seconds: keeps every transition on the beat
  "base": { "x": -0.08, "z": 0.712, "yaw": 0 },  // published on /global_pose, glides at constant speed over the hold
  "target": {
    "joint_names": ["neck_yaw", "l_shoulder", "r_shoulder", "l_hip", "l_knee", "r_hip", "r_knee", ...],
    "positions":   [ 0.25,       0.6,          -0.7,         -0.45,   1.3,      0.18,    0.0,     ...] },
  "on_arrival": "next",
  "transitions": [{ "name": "next", "next_state": "moonwalk_a_2" }] }
    • hold makes the machine wait out the beat, and schedules the next transition from the beat grid instead of from "now", so the loop is 24.00 s every time and stays locked to the music (I measured it over two loops).
    • base moves the robot's root along /global_pose. With a hold it moves at constant speed, which is the moonwalk glide.

    Both are optional and ignored by plain choreographies. They live only in the demo-only finite_state_machine node, so the graded runtime (make run) is unchanged.

    How the robot is drawn

    The viewer is its own client: it never does kinematics. It only draws what the runtime says.

    1. Parse the URDF for looks only. For each link I read the first <visual>: a box, cylinder or sphere, its origin offset, and its colour. Each becomes a three.js mesh inside a Group for that link, with matrixAutoUpdate = false because the runtime's matrix is the whole transform.
    2. The runtime does the forward kinematics. robot_state_publisher turns /joint_states into a /tf tree. It uses my own quaternion maths and the standard-library XML parser, with no kinematics or transform library. robot_world_state_publisher composes the tree with /global_pose and publishes one 4×4 matrix per link on /xform_world.
    3. Put each group where its matrix says. The matrices are column-major, which is exactly the layout of Matrix4.fromArray, so there is nothing to transpose.
    4. Convert z-up to y-up once. URDF is z-up and three.js is y-up. Instead of converting every matrix, all link groups sit inside a single parent rotated −90° about x.
    const zup = new THREE.Group();
zup.rotation.x = -Math.PI / 2;                  // URDF z-up  ->  three.js y-up, for every link at once

// per frame: the runtime's matrix for each link, column-major, goes straight in
group.matrix.fromArray(entry.matrix);
group.matrixWorldNeedsUpdate = true;
    Why a replay and not a live connection? A static site cannot reach a Python runtime on my laptop, so this page plays back one recorded loop (assets/replay.json, 634 frames of 25 links, about 1 MB) that I captured from the real /xform_world stream with tools/record_replay.py. Between two recorded frames (~33 ms apart) the page interpolates linearly. The development viewer, viewer/server.py, subscribes to the live topic instead.

    The "Try it yourself" tab is different: it runs live, so it needs the maths in the browser. js/sim.js is a JavaScript port of my runtime's joint servo, state machine and forward kinematics. To check the port I ran the dance through it and compared every link's matrix with the recording from the Python runtime: the average difference per matrix entry is about 0.01 (rotation entries run from −1 to 1, positions are in metres). The only bigger gaps are at the instant a beat changes, when an arm can be moving at over 30 rad/s, so a 30 ms timing difference in the recording shows up. The check is in tools/sim_vs_replay.html.

    A detail I had to fix along the way: the spec only requires /xform_world at 5 Hz or faster, and the reference rate is 10 Hz, which looks choppy for a dance. Under make demo the publishers run at 30 Hz; make run keeps the reference rate.

    The synchronisation is the same trick in both directions: the dance and the music share one clock. While the music plays, the dance reads its time from the audio hardware clock, so they cannot drift apart, and clicking Music on mid-dance starts the beat on the next 16th note that lines up with where the dancer is.
